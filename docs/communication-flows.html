Communication Flows & Privacy

e2eMoQ / moqplay · working reference · revised 15 August 2026 · companion to trust-model (who-can-see-what) and security-architecture (content encryption).

This traces the wire-level messages between the app, the two browser roles (broadcaster / watcher), the backend (broker + fleet), and the chat channel — with a privacy annotation on every hop, so we can see exactly how a user could be identified, targeted, or revealed, and where they're protected. Written to expose leaks, not to reassure.

Headline: the tokens and the media path are clean, but precise geolocation (lat/lon) is captured server-side and persisted in D1 for both broadcasters and viewers, and one endpoint (GET /api/stats/stream/:id/viewers) re-exposes every viewer's stored geo publicly. That is the single biggest deanonymization surface today (§6).

1. Global facts (apply to every flow)

  • OAuth is disabled → no account identity. getAuthenticatedUser() returns a hardcoded anon user (id:1) — index.ts:1459, auth.ts:25. Every user_id written is 1.
  • Every browser→Worker call is a Cloudflare request, so Cloudflare/the Worker always sees the caller's IP and request.cf (lat/lon/city/region/country/colo/asn/asOrganization) — even when the body carries no identity.
  • Tokens are clean. MoqClaims = {put, get:[<broadcastName>], exp, cluster?} (moq-token.ts:43). No IP, geo, email, or account id in any token — only the pseudonymous stream id + expiry.

2. The four channels

1 · Control

browser ↔ Worker (/api/*). Carries IP + precise geo; some persisted to D1.

2 · Broker

Worker ↔ broker. Server-to-server; forwarded precise geo, no viewer IP.

3 · Chat

browser ↔ per-stream Durable Object (WebSocket). Plaintext; separate from media & relay.

4 · Media

browser ↔ relay box (WebTransport). Box sees browser IP; media is ciphertext (fleet flow).
Resolved 2026-08-15 — there is no longer a fifth channel. A Discovery plane used to sit here: browser ↔ public pkarr relays, exposing the browser IP and the nodeId being published or looked up to third-party infrastructure outside Cloudflare. The DHT path was removed from e2eMoQ entirely. No browser contacts a pkarr relay, and nothing about any broadcast is published to a public network. The two ⚠ findings in Group E below are closed.

4. Chat — the separate plaintext channel

Chat lives in chat-room.ts (Durable Object), chat-client.ts (browser), route at index.ts:475. It is completely separate from the media path and the relay.

  • Transport: WebSocket wss://<host>/api/streams/<id>/chat → one Durable Object per stream; fan-out to all sockets (chat-room.ts:66).
  • Message on the wire: client sends {type:"msg", name, text}; DO stamps {id, name, text, ts}. No user id, token, pubkey, stream id, or IP in the message.
  • Identity = a self-chosen, spoofable display name. No auth required to chat (route checks only chat_enabled). Anyone can chat anonymously. ⚠ Footgun: if signed in, the client pre-fills the real user.name into the handle (chat-client.ts:22).
  • Storage: the last 50 messages persist in DO storage with no TTL and no deletion on broadcast end (chat-room.ts:61).
  • Who reads it: plaintext, server-visible — Cloudflare and the broadcaster see 100% of content + claimed names. The relay never sees chat. Not covered by media AES-GCM.
  • IP/metadata: Cloudflare sees the socket IP at the edge, but the chat code never reads, logs, or stores it; messages carry no IP. Presence = live socket count only.

5. What actually identifies a user

  1. IP + Cloudflare geo/ASN — ambient on every browser call. The real deanonymizer.
  2. Precise geo (lat/lon) — captured server-side and persisted in D1 for broadcasters (broadcast_events) and viewers (watch_events), and re-exposed (one endpoint publicly).
  3. Stream id — pseudonymous; a stream, not a person.
  4. Chat display name — self-chosen; self-doxxing vector (esp. auto-filled real name).
  5. Email — only on the admin surface; inert for normal users (OAuth off).
  6. Tokens carry none of the above.

6. How a user gets revealed — ranked exposures

High — Persisted precise geolocation, one endpoint public. Lat/lon captured from request.cf and stored in D1 for both broadcasters and viewers, then re-exposed by GET /api/stats/live and — critically — the public GET /api/stats/stream/:id/viewers. Anyone holding a stream id can read the precise stored location of everyone who watched it. Top risk; live today.
High — Precise viewer geo deliberately forwarded to an external broker. brokerHints sends {lat,lon,country,colo} to moqcdn.net/cdnadmin on every brokered assign.
Medium — Raw browser IP exposed to third-party infrastructure. Direct browser→relay shows the untrusted fleet box the real IP + pseudonymous stream id (network floor). Partly resolved 2026-08-15: the pkarr half is gone — no browser contacts a public DHT relay, so no third party outside Cloudflare and the fleet box sees an IP↔content linkage. The network floor against the fleet box remains, and is what a VPN or Tor addresses.
Medium — Chat: plaintext + persistence + name footgun. All chat is plaintext to Cloudflare and the broadcaster; last 50 messages persist with no expiry / no end-of-broadcast deletion; a signed-in user's real name is auto-filled into the handle.
Resolved 2026-08-15 — Node-id media path is not encrypted. The path was removed rather than encrypted. There is now exactly one media path and it is always end-to-end encrypted, so "no plaintext" holds everywhere without exception.
Low / operational — Admin surface. A hardcoded admin bearer (static password in source) guards endpoints that can return email addresses. Fix regardless of the privacy model.

7. What already protects users

  • No accounts. OAuth off → no durable account identity; every user is anon id:1.
  • Clean tokens. No IP/geo/email/account id in any JWT — only stream id + exp.
  • Relay is content-blind and chat-blind. Media is ciphertext (fleet flow); chat never touches the relay.
  • No IP in tokens, messages, or chat records. IP is transient at the edges — except the geo derived from it that is stored (§6 High).
  • Media path carries no geo; geo lives only in the control plane.

8. Recommendations (ranked to the high-privacy bar)

  1. Stop persisting precise geo; coarsen to US-state / non-US-country only (trust-model §7.1) in both broadcast_events and watch_events. Consider not storing viewer geo at all — does watch_events need to exist?
  2. Lock down or remove the geo-exposing stats endpoints now. GET /api/stats/stream/:id/viewers is public and leaks stored viewer geo; /api/stats/live exposes it broadly. Gate behind the operator or strip geo. (Live leak — highest urgency.)
  3. Coarsen the geo forwarded to the broker (brokerHints) to the same label.
  4. Chat: don't auto-fill the real account name; add a TTL / delete DO storage on broadcast end; document that chat is plaintext-to-Cloudflare (or move to E2E chat later).
  5. Encrypt or retire the node-id media path so "no plaintext" holds everywhere. Done 2026-08-15 — retired.
  6. Replace the hardcoded admin bearer with a Worker secret; keep emails off any normal-user response.
  7. pkarr IP exposure (node-id flow): self-host a pkarr relay or proxy put/get through the Worker. Done 2026-08-15 — resolved by removing the flow, so neither mitigation is needed. Cross-fleet routing never depended on it: the broker already places viewers given the origin.
  8. Relay IP exposure is the network floor — the user's own tool (Tor/VPN); can't be removed in software. Document honestly.
