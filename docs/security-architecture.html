e2eMoQ.tv

Architecture — Relay-Blind Streaming & the Watch-by-Pubkey Federated Multi-CDN

Version 7 · July 2026

e2eMoQ streams live video over Media over QUIC (MoQ). Two design commitments shape the system. First, its security model separates who may reach a relay from who may watch the media, so the servers moving the bytes never see the content (§1–6). Second, streams are named by self-generated cryptographic identities, and this document is explicit about how those names are routed to a live relay today versus where that routing is headed (§7).

1. The components

  • Browser — runs the MoQ publisher (broadcaster) or watcher (viewer), built on the open-source MoQplay engine. This is the only place plaintext media ever exists; frames are encrypted before they leave the tab and decrypted only after they arrive in another tab. The browser also mints each stream's cryptographic identity (§7.1).
  • e2emoq Worker (Cloudflare) — the control brain. It mints per-session CDN tokens and holds the D1 database recording each broadcast. It never touches media bytes and never holds a media key.
  • CDN — cdn.moq.pro, the data plane. Browsers reach it over WebTransport/QUIC and it fans one publisher out to many viewers. It places viewers on its own nearest relay; e2eMoQ does not choose or operate relays. It only ever handles ciphertext.
How the app gets a relay. It does not ask for one. There is no provisioning step and no server-to-server call anywhere in this system. The relay is always cdn.moq.pro; the broadcast path is <root>/<id>.hang under the account root. The Worker signs a short-lived token scoped to that one path and hands it to the browser, which presents it to the CDN itself. Nothing about the viewer — no IP, no location, no account — is ever sent from us to the CDN, because we never call it.

2. Two distinct credential layers

The most important idea in the system: there are two token layers doing unrelated jobs. Confusing them is the single biggest source of error.

Layer 1 — the publish code (admission)

A stateless credential that answers one question: may this person broadcast at all? It is the same value for every broadcaster, identifies nobody, and is verified against the PUBLISH_SECRET in the Worker's secret store. It is minted automatically on first go-live, so most broadcasters never see it. It says nothing about which broadcast — that is the job of the signed claim beside it (§7.1) — and it never reaches the CDN.

Layer 2 — per-broadcast MoQ tokens (session capability)

Short-lived EdDSA (Ed25519) JWTs that authorize one browser to do one thing on one relay for a bounded time. Minted fresh per session by the Worker and couriered to the browser, which presents them to cdn.moq.pro. Their put/get claims are scoped to exactly one broadcast name (<id>.hang under the account root), and they are signed with e2eMoQ's own Ed25519 private key (BYOK). moq.pro holds only the public half, registered once, so it can verify our tokens and can never mint one.

Key separation. The publish code proves a person may broadcast to us. The MoQ token proves one browser may do one thing to the CDN, signed by e2eMoQ and verified with a public key only. Neither token can decrypt media — that is a third, independent secret we never hold (§5).

3. Broadcast flow — going live

browser                        Worker (e2emoq)              cdn.moq.pro
  |  mint 5-char stream id        |                              |
  |  POST /api/stats/broadcast    |                              |
  |    + publish code             |                              |
  |    + Ed25519 claim over id    |                              |
  | ----------------------------> |                              |
  |                               |  mintMoqProTokenEd25519(     |
  |                               |    MOQ_PRO_JWK, {            |
  |                               |      root,                   |
  |                               |      put: ["<id>.hang"],     |
  |                               |      get: ["<id>.hang"],     |
  |                               |      exp }) -> jwt           |
  |  <-- { relay, path, jwt } --- |  (no content key: the Worker has none)
  |                               |  (no call to the CDN: none is needed)
  |                                                              |
  |  derive media key locally:                                   |
  |    HKDF(link secret from #k=, info="e2emoq-content-key-v1")   |
  |                                                              |
  |  connect cdn.moq.pro, publish AES-GCM-encrypted frames -----> |
  1. The browser mints a 5-char stream id (§7.1) and uses it as the broadcast name, then calls the Worker's POST /api/stats/broadcast, presenting a publish code and a signed claim over that id.
  2. The Worker mints a JWT (mintMoqProTokenEd25519) carrying put and get scoped to the single broadcast name, plus an expiry, signed with e2eMoQ's own Ed25519 private key. There is no call to the CDN at this or any other step.
  3. The browser generates a link secret — and, if the broadcaster switched on Protect, a passcode as well — and derives the 256-bit AES-GCM media key with HKDF-SHA256 (info = "e2emoq-content-key-v1"). The secret lives in the share link's # fragment, which browsers never transmit; the passcode is never in the link at all. So no content key is created by, sent to, or stored on the server, and neither is either input to it (§5).
  4. The browser connects to cdn.moq.pro presenting the JWT. The CDN validates it against e2eMoQ's registered public key; the put scope authorizes publishing that one name. Frames are AES-GCM encrypted in the browser before transmission.

4. Playback flow — joining a stream

browser   GET /api/streams/<id>/route --> Worker
                                          |  look up relay in D1 (co-locate on publisher's relay)
                                          |  mintEd25519Token(privKey, { put: [], get: [<name>], exp }) -> viewer jwt
          <-- { relay, jwt, encrypted, content_key: null } --
          derive the same media key from the #k= fragment of the link the viewer was given
          connect wss://<relay>/?jwt=<viewer jwt>,  pull ciphertext, decrypt in browser
  • The viewer token is put: [], get: [<name>] — subscribe-only. It cannot publish, so a viewer can never hijack the broadcast name.
  • The viewer is placed on a nearby relay by moq.pro, using its own global network. e2eMoQ takes no part in that decision and sends the CDN nothing about the viewer.
  • content_key is always null on this response. Confidentiality is not enforced by the Worker withholding anything — it is enforced by the Worker never having the key. A viewer without the # fragment connects, pulls ciphertext, and decodes nothing.

5. The encryption layer is orthogonal to the tokens

MoQ tokens govern access to the relay. The media key governs confidentiality of the media, and it is a wholly separate secret that no server ever holds:

  • Derived in the browser, never transmitted. The broadcaster generates a random link secret and places it in the share link's fragment, after the #. Browsers do not send that part of a URL to any server — so it reaches no Worker, no database, no log, and no CDN. Both ends derive the AES-256-GCM key from it with HKDF-SHA256.
  • The passcode is a mandatory second factor, and is not in the link. Every broadcast mints one when the page loads; there is no path that publishes without one. It is stretched with PBKDF2-SHA256 (210,000 iterations, salted per stream) and mixed into the derivation, so a link on its own never plays and the two secrets have to travel by different channels to be useful together. Nothing can confirm a guess: a wrong passcode yields a wrong key and the media fails to authenticate, with no server holding anything to compare a guess against.
  • Re-keying is a broadcaster action. A new passcode re-derives in place and cuts off anyone holding the old one, without changing the link. It is applied at the next group boundary rather than mid-group, so no group is ever split across two keys — a viewer arriving during a re-key would otherwise receive a keyframe it could not decrypt and could render nothing for that group. The lockout is therefore bounded by the keyframe interval, ~2s, rather than being instantaneous.
  • Separated by HKDF info. Media, chat, and the route-authorization tag derive independently from the same secret, so compromising one does not yield another. The chat Durable Object relays text it cannot read.
  • This is what relay-blind means: a compromised, subpoenaed, or merely curious relay operator — or we ourselves — see only ciphertext. Encryption is mandatory; there is no plaintext publishing path.
  • The consequence worth stating plainly: we cannot decrypt a broadcast, cannot produce a recording of one, and could not comply with a demand to hand one over. Not as policy — the key does not exist on our side, and neither of the two secrets it is built from has ever been sent to us.
  • The one exception, and its exact shape. A viewer filing an abuse report may attach a single still frame, captured from the player on their own device — which necessarily decoded the video in order to display it. It is shown to them before it is sent and removable with one click. This is the only plaintext broadcast content that ever reaches our storage, and it does not weaken anything above: a JPEG is not a key, decrypts nothing, and describes one instant chosen by a viewer rather than a stream. It is bounded four ways — the reporter consents, it is one frame and not a clip, the stored bytes are verified to carry a JPEG marker so the type is ours to assert rather than the reporter's to declare, and it is deleted after thirty days while the record of the complaint remains. The alternative it replaced was an operator ending someone's broadcast on an anonymous stranger's unverifiable word.

This replaced an earlier design in which the Worker generated the content key, stored it in D1, and released it to viewers it considered authorized. That model made confidentiality depend on our own good behaviour and on the integrity of a database we hold. Keys derived from the link fragment remove us from the trust set entirely; the D1 column that held them was dropped and its contents destroyed.

7. Stream addressing & routing

A live stream needs a handle a viewer can be given, and that handle must resolve to a concrete network location — a relay host:port. e2eMoQ has exactly one way of doing this. It used to have two; §7.4 records what the second was and why it is gone.

7.1 How a stream is named — and why the name is not the secret

A broadcast's handle is a 5-character stream id ([a-z0-9]{5}), minted in the browser and collision-checked against the Worker. It is the MoQ broadcast name and the path in the share link. That is all it is: the id carries no authority in either direction.

  • It does not authorize watching. The capability is the link secret in the fragment after #, which browsers never transmit — plus the passcode, if the broadcaster armed Protect, which is never in the link at all (§5). Knowing a stream id, even guessing one, yields nothing to decrypt.
  • It does not authorize publishing. Going live needs a publish code (admission) and a signed claim over the id. The browser mints a fresh, non-extractable Ed25519 keypair per broadcast and signs e2emoq-claim-v1|<id>|<challenge>; the Worker records the public half against the live row and refuses a second claimant. The keypair is fresh every broadcast on purpose — a reused key would make one broadcaster's streams linkable to each other by anyone who saw it.

7.2 Routing — moq.pro places the viewer

There is no routing model to choose and no autoscaler to ask. The relay is always cdn.moq.pro and the broadcast path is <root>/<id>.hang, so the Worker can name the destination without looking anything up:

publish:    { root, put: ["<id>.hang"], get: ["<id>.hang"], exp }
subscribe:  { root, put: [],              get: ["<id>.hang"], exp }
                    signed Ed25519 with MOQ_PRO_JWK; moq.pro holds only the public half

A viewer calls the Worker's /route, which authorises them by a tag derived from the share-link secret and returns a subscribe-only token. The browser presents it to cdn.moq.pro, and moq.pro selects the nearest relay itself across its own network. e2eMoQ neither knows nor influences which one, and — because the Worker never calls the CDN — the CDN learns nothing about a viewer from us. It sees only the connection the browser makes directly, which is the network floor described in §6.

7.3 There is no directory, and no discovery

A viewer reaches a broadcast one way: by holding the link. There is no index, no lookup service, no public record, and nothing published to any outside network that would reveal that a stream exists or where it is carried. Nothing about an e2eMoQ broadcast appears in any public directory, DHT, or index.

The consequence worth drawing out: a stream id is not a secret, and it is not meant to be. Guessing one, or sweeping the whole five-character space, tells an attacker only whether something is live. It yields no media, because the key was never on this side of the wire.

8. Teardown

On stop or tab close, the browser calls POST /api/stats/broadcast/:id/end. The Worker marks the broadcast ended in D1. Nothing has to be reclaimed: no relay was ever provisioned, and the tokens simply expire. Content keys are per-session; a restarted broadcast receives a fresh key, so previously distributed keys cannot decrypt a new session.

The model in one line

A publish code proves a person may broadcast to us; the Worker mints short-lived, tightly-scoped EdDSA tokens — signed with e2eMoQ's private key, verified by moq.pro with the public half it can never mint from — that prove this browser may do one thing on one broadcast path; and a separate media key, derived in the browser from a link fragment that reaches no server, keeps the video private end-to-end.
