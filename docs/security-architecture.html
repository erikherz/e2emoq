Architecture — Relay-Blind Streaming & the Watch-by-Pubkey Federated Multi-CDN

Version 7 · July 2026

e2eMoQ streams live video over Media over QUIC (MoQ). Two design commitments shape the system. First, its security model separates who may reach a relay from who may watch the media, so the servers moving the bytes never see the content (§1–6). Second, streams are named by self-generated cryptographic identities, and this document is explicit about how those names are routed to a live relay today versus where that routing is headed (§7).

1. The components

  • Browser — runs the MoQ publisher (broadcaster) or watcher (viewer), built on the open-source MoQplay engine. This is the only place plaintext media ever exists; frames are encrypted before they leave the tab and decrypted only after they arrive in another tab. The browser also mints each stream's cryptographic identity (§7.1).
  • e2emoq Worker (Cloudflare) — the control brain. It authenticates to the relay fleet, mints per-session tokens, and holds the D1 database mapping each broadcast to its relay. It never touches media bytes and never holds a media key.
  • Broker / control plane — moqcdn.net/cdnadmin, the CDN broker (the cdnadmin console + POST /cdn/assign). The Worker asks it to place a relay for a broadcast (by name); the broker geo-selects a box across the four regional fleets, boots or reuses a micro-relay, and is fail-closed: a missing or wrong customer token yields 401. The Worker never contacts a relay box directly and never holds a box bearer — the broker owns box topology and holds the per-box provisioning bearers itself.
  • Relays — {ams,was,tok}.moqcdn.net / sca.gpcmoq.com :800X, the data plane across four regions. Hermit-OS unikernels under Linux KVM, each serving one broadcast on a dedicated UDP port. Browsers reach them over WebTransport/QUIC; a relay can also pull from another fleet's origin relay over iroh or by host:port QUIC (§7.3). On the relay-blind flow they only ever handle ciphertext.
How the app gets a relay. Provisioning — getting an origin box, and an edge that pulls from it — runs one way, content-blind at the fleet: the Worker calls the moqcdn broker (POST moqcdn.net/cdn/assign) with a cdn_ customer token, and the broker geo-places a box across the four regional fleets. The Worker never holds a box bearer and never talks to a relay directly — the broker owns box selection and authenticates to each box itself. (An earlier build also supported a direct mode, where the app called a fleet box's /assign with that box's tmq_ bearer; the deployed system no longer uses it — brokered is the only path.) There is no separate discovery step: the Worker knows where it placed the origin, and hands it to the broker when a viewer arrives (§7.2).

2. Two distinct credential layers

The most important idea in the system: there are two token layers doing unrelated jobs. Confusing them is the single biggest source of error.

Layer 1 — the broker customer token (tenant identity)

The secret CDN_API_TOKEN — a cdn_ customer token issued by the moqcdn cdnadmin — is e2eMoQ's customer identity with the broker. The Worker sends it as Authorization: Bearer … to moqcdn.net/cdn/assign. It is long-lived, lives only in the Worker's secret store, and never reaches a browser or a relay. It proves e2eMoQ-the-tenant to the broker, nothing finer-grained. The broker in turn holds the per-box provisioning bearers (tmq_, host-scoped) and authenticates to each relay itself — the Worker never sees them. (The token is broker-specific: a cdn_ token is an HMAC under that broker's master key, so a token minted by one broker is meaningless to another.)

Layer 2 — per-broadcast MoQ tokens (session capability)

Short-lived EdDSA (Ed25519) JWTs that authorize one browser to do one thing on one relay for a bounded time. Minted fresh per session by the Worker, couriered to the browser, and presented to the relay in the ?jwt= connection parameter. Their put/get claims are scoped to exactly one broadcast name (e.g. moqplay.com/<id>.hang), and they are signed with e2eMoQ's own private key (BYOK, kid e2emoq-533d711d). The relay validates the signature against e2eMoQ's public verify_jwk, which the broker has mapped onto the box — the box holds only the public half, so it can verify but can never mint.

Key separation. The customer token proves the company to the broker. The MoQ token proves one browser to one relay, signed by e2eMoQ and verified by the box with a public key only. Neither token can decrypt media — that is a third, independent secret (§5).

3. Broadcast flow — going live

browser                      Worker (e2emoq)      moqcdn broker        relay
  |  mint 5-char stream id      |                            |                    |
  |  POST /api/stats/broadcast  |                            |                    |
  | --------------------------> |  POST /cdn/assign          |                    |
  |                             |    { broadcast:            |                    |
  |                             |      moqplay.com/<id>.hang }|                    |
  |                             |  Authorization: Bearer     |                    |
  |                             |    <cdn_ customer token>   |                    |
  |                             | -------------------------> |  geo-place a box   |
  |                             |  <--------- { relay } ----- |                    |
  |                             |                                                 |
  |                             |  mintEd25519Token(privKey, {                    |
  |                             |    put: [moqplay.com/<id>.hang],                 |
  |                             |    get: [moqplay.com/<id>.hang],                 |
  |                             |    exp }, kid=e2emoq-533d711d) -> jwt        |
  |  <-- { relay, jwt } -------- |  (no content key: the Worker has none)          |
  |                                                                               |
  |  derive media key locally:                                                    |
  |    HKDF(link secret from #k=, info="e2emoq-content-key-v1")               |
  |                                                                               |
  |  connect wss://<relay>/?jwt=<jwt>,  publish AES-GCM-encrypted frames --------> |
  1. The browser mints a 5-char stream id (§7.1) and uses it as the broadcast name, then calls the Worker's POST /api/stats/broadcast, presenting a publish code and a signed claim over that id.
  2. The Worker calls the broker POST moqcdn.net/cdn/assign { broadcast: moqplay.com/<id>.hang } with the cdn_ customer token. The broker geo-places a relay across the four regional fleets and returns { relay } — a host:port. The Worker never sees a box bearer or a per-stream key.
  3. The Worker mints a JWT (mintEd25519Token) carrying put and get scoped to the single broadcast name, plus an expiry, signed with e2eMoQ's own Ed25519 private key (kid e2emoq-533d711d).
  4. The browser generates a link secret and a passcode, and derives the 256-bit AES-GCM media key from both with HKDF-SHA256 (info = "e2emoq-content-key-v1"). The secret lives in the share link's # fragment, which browsers never transmit; the passcode is never in the link at all. So no content key is created by, sent to, or stored on the server, and neither is either input to it (§5).
  5. The browser connects to wss://<relay>/?jwt=<jwt>. The relay validates the JWT against e2eMoQ's public verify_jwk (mapped onto the box by the broker); the put scope authorizes publishing that name. Frames are AES-GCM encrypted in the browser before transmission.

4. Playback flow — joining a stream

browser   GET /api/streams/<id>/route --> Worker
                                          |  look up relay in D1 (co-locate on publisher's relay)
                                          |  mintEd25519Token(privKey, { put: [], get: [<name>], exp }) -> viewer jwt
          <-- { relay, jwt, encrypted, content_key: null } --
          derive the same media key from the #k= fragment of the link the viewer was given
          connect wss://<relay>/?jwt=<viewer jwt>,  pull ciphertext, decrypt in browser
  • The viewer token is put: [], get: [<name>] — subscribe-only. It cannot publish, so a viewer can never hijack the broadcast name.
  • The viewer is geo-routed to its nearest regional fleet. When that fleet is the origin's own box the broker serves it directly (co-location, the fast path); otherwise the broker hands that fleet the origin's host:port plus a subscribe-scoped pull token and it cluster-pulls the origin over QUIC. Model A media therefore spans regions — co-location is an optimization, not a requirement (live and proven 2026-07-19; §7.2).
  • content_key is always null on this response. Confidentiality is not enforced by the Worker withholding anything — it is enforced by the Worker never having the key. A viewer without the # fragment connects, pulls ciphertext, and decodes nothing.

5. The encryption layer is orthogonal to the tokens

MoQ tokens govern access to the relay. The media key governs confidentiality of the media, and it is a wholly separate secret that no server ever holds:

  • Derived in the browser, never transmitted. The broadcaster generates a random link secret and places it in the share link's fragment, after the #. Browsers do not send that part of a URL to any server — so it reaches no Worker, no database, no log, and no CDN. Both ends derive the AES-256-GCM key from it with HKDF-SHA256.
  • The passcode is a mandatory second factor, and is not in the link. Every broadcast mints one when the page loads; there is no path that publishes without one. It is stretched with PBKDF2-SHA256 (210,000 iterations, salted per stream) and mixed into the derivation, so a link on its own never plays and the two secrets have to travel by different channels to be useful together. Nothing can confirm a guess: a wrong passcode yields a wrong key and the media fails to authenticate, with no server holding anything to compare a guess against.
  • Re-keying is a broadcaster action. A new passcode re-derives in place and cuts off anyone holding the old one, without changing the link. It is applied at the next group boundary rather than mid-group, so no group is ever split across two keys — a viewer arriving during a re-key would otherwise receive a keyframe it could not decrypt and could render nothing for that group. The lockout is therefore bounded by the keyframe interval, ~2s, rather than being instantaneous.
  • Separated by HKDF info. Media, chat, and the route-authorization tag derive independently from the same secret, so compromising one does not yield another. The chat Durable Object relays text it cannot read.
  • This is what relay-blind means: a compromised, subpoenaed, or merely curious relay operator — or we ourselves — see only ciphertext. Encryption is mandatory; there is no plaintext publishing path.
  • The consequence worth stating plainly: we cannot decrypt a broadcast, cannot produce a recording of one, and could not comply with a demand to hand one over. Not as policy — the key does not exist on our side, and neither of the two secrets it is built from has ever been sent to us.
  • The one exception, and its exact shape. A viewer filing an abuse report may attach a single still frame, captured from the player on their own device — which necessarily decoded the video in order to display it. It is shown to them before it is sent and removable with one click. This is the only plaintext broadcast content that ever reaches our storage, and it does not weaken anything above: a JPEG is not a key, decrypts nothing, and describes one instant chosen by a viewer rather than a stream. It is bounded four ways — the reporter consents, it is one frame and not a clip, the stored bytes are verified to carry a JPEG marker so the type is ours to assert rather than the reporter's to declare, and it is deleted after thirty days while the record of the complaint remains. The alternative it replaced was an operator ending someone's broadcast on an anonymous stranger's unverifiable word.

This replaced an earlier design in which the Worker generated the content key, stored it in D1, and released it to viewers it considered authorized. That model made confidentiality depend on our own good behaviour and on the integrity of a database we hold. Keys derived from the link fragment remove us from the trust set entirely; the D1 column that held them was dropped and its contents destroyed.

7. Stream addressing & routing

A live stream needs a handle a viewer can be given, and that handle must resolve to a concrete network location — a relay host:port. e2eMoQ has exactly one way of doing this. It used to have two; §7.4 records what the second was and why it is gone.

7.1 How a stream is named — and why the name is not the secret

A broadcast's handle is a 5-character stream id ([a-z0-9]{5}), minted in the browser and collision-checked against the Worker. It is the MoQ broadcast name and the path in the share link. That is all it is: the id carries no authority in either direction.

  • It does not authorize watching. The capability is the link secret in the fragment after #, which browsers never transmit, together with the passcode, which is never in the link at all (§5). Knowing a stream id — even guessing one — yields nothing to decrypt, and neither does holding the whole link without the passcode.
  • It does not authorize publishing. Going live needs a publish code (admission) and a signed claim over the id. The browser mints a fresh, non-extractable Ed25519 keypair per broadcast and signs e2emoq-claim-v1|<id>|<challenge>; the Worker records the public half against the live row and refuses a second claimant. The keypair is fresh every broadcast on purpose — a reused key would make one broadcaster's streams linkable to each other by anyone who saw it.

Keep this identity separate from the origin relay's iroh EndpointId, which is a 64-hex transport address derived from the relay's HERMIT_IROH_SECRET, chosen by the relay at boot, and used only for relay→relay dialling (§7.3). It never names a stream and never appears in a share link.

7.2 Routing model A — broker by name

This is what e2eMoQ runs in production. The name is resolved to a relay by the TinyMoQ autoscaler — not by the id itself:

Worker --GET https://ams.moqcdn.net/assign?broadcast=moqplay.com/<id>.hang--> autoscaler
        Authorization: Bearer <tenant token>
autoscaler -->  { relay: "ams.moqcdn.net:800X", key, byok:false }
                (boots or reuses a micro-relay for this broadcast on UDP 800X)

The address handed back is a host:port. Viewers do not run discovery themselves: they call the Worker's /route, which looks up the broadcast's origin relay in D1 and hands the broker that origin plus a subscribe-scoped pull token. The broker geo-routes the viewer to its nearest healthy fleet: if that fleet is the origin box it serves direct (co-location, the fast path); otherwise that fleet cluster-pulls the origin over host:port QUIC using the pull token. Relays no longer have to be islands — a Model A viewer can be served from a fleet in a different region than the origin, the media pulled cross-fleet (live 2026-07-19). The edge authenticates its pull by presenting the viewer's own subscribe-scoped token over the host:port cluster-connect — the relay authorizes by scope alone, with no cluster flag and no anonymous sentinel.

Viewer steering. /route places a viewer three ways: Mode A (origin) — served directly on the origin's box when the viewer is nearest it; Mode B (cross-fleet edge) — the viewer's geo-nearest fleet pulls from the origin, authorized by a subscribe-scoped pull token (the same scope as the viewer token, with no cluster flag — the relay authorizes the pull by scope alone); Mode C (enterprise on-net) — a private relay on the viewer's own network (ASN-gated), so media never traverses a public server. Under the brokered production path, Modes A and B are the broker's automatic choice per viewer geo — no override needed — and Mode B is live and proven (2026-07-19: a viewer geo-forced to Amsterdam was served by the ams fleet cluster-pulling a Washington DC origin over host:port). The broker owns co-location detection by hostname, so it never hair-pins. (This was carried on the /cdn/assign contract all along, but the brokered /route previously sent only {broadcast} — dropping origin and pull — so auto-geo Mode B did not actually pull until the Worker was fixed to forward them.) In every mode the content key is delivered by the same rule (§5) and the relay-blind property holds.

7.3 The relay fleet

The data plane is a fleet of micro-relays. The autoscaler boots each on demand as a Hermit-OS unikernel — a single-address-space Rust image running under Linux KVM — listening on a dedicated UDP port. Each relay is per-broadcast keyed and short-lived; idle relays are reaped and their /released slots recycled. The browser↔relay hop is always WebTransport/QUIC to a host:port. For cross-fleet federation, a relay also carries an iroh endpoint of its own (derived from its HERMIT_IROH_SECRET): an edge relay dials the origin relay by that EndpointId over iroh, using iroh's own relay-to-relay discovery — NAT-friendly, so an origin needs no public host:port. This is a hop between two boxes on the fleet: the browser is never party to it, and it publishes nothing about the broadcast. (Where both origin and edge have routable addresses, native moq-relay cluster-connect by host:port is still available; the ?xport=iroh selector picks between them.)

7.4 What was removed — watch-by-pubkey and the DHT

Until August 2026 e2eMoQ carried a second addressing model alongside the one above. A broadcaster could mint an Ed25519 keypair in the browser, use base32(publicKey) as the stream's name, and self-publish a signed pkarr (BEP44) record to the public BitTorrent Mainline DHT mapping that key to the origin relay's iroh EndpointId. A viewer resolved the key straight off the DHT — no directory server anywhere in the path — and the Worker provisioned an edge to pull from the resolved origin.

It worked, and it was proven cross-fleet. It was removed anyway, for two reasons that outweigh the capability it added:

  • It was never what did the cross-fleet routing. The brokered path in §7.2 already hands the broker the origin plus a subscribe-scoped pull token and lets it place the viewer on their geo-nearest fleet. Discovery-by-DHT was a second implementation of a problem already solved — and solved without publishing anything.
  • It published in the clear, to a public network. The record was world-readable by design: anyone crawling the DHT could see that a given key was live and which origin carried it. The media on that path was also deliberately not end-to-end encrypted, because the point was that a stranger's client could subscribe without a content key. Both properties are the inverse of what the rest of this system promises, so the codebase was asserting two contradictory privacy models at once.

What remains is a single path: one stream handle, always encrypted, decodable only by someone holding both the share link and the broadcast's passcode. Nothing about a e2eMoQ broadcast is published to any public directory, DHT, or index.

Retired with it: the Worker's /api/publish and /api/edge provisioning routes, and the last references to the standalone luke.moqcdn.net directory (whose /api/register / /api/resolve service had already been withdrawn).

8. Teardown

On stop or tab close, the browser calls POST /api/stats/broadcast/:id/end. The Worker marks the broadcast ended in D1; the broker reclaims the relay slot. Content keys are per-session; a restarted broadcast receives a fresh key, so previously distributed keys cannot decrypt a new session.

The model in one line

The customer token proves e2eMoQ to the broker; the broker geo-places a relay and maps e2eMoQ's public verify key onto it; the Worker mints short-lived, tightly-scoped EdDSA JWTs — signed with e2eMoQ's private key — that prove this browser to this relay; and a separate media key, derived in the browser from a link fragment that reaches no server, keeps the video private end-to-end.
